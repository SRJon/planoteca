GUIA · PLANOTECA · PRIMEIRO DEPLOY

Guia de provisionamento

Passo a passo para criar as contas da Planoteca do zero e colocar o primeiro deploy no ar — banco, arquivo, login, API e front, nessa ordem.

TL;DR

Cinco serviços, todos em plano gratuito: Neon (banco), Cloudflare R2 (arquivos), Firebase (login), Render (API) e Vercel (front). A ordem importa: o Render precisa das chaves do Neon e do R2 para subir, e o Vercel precisa da URL do Render para o build. Fazer fora de ordem obriga a voltar e refazer um passo.

01 Neon — banco

Criar um projeto novo, nome planoteca. Região aws-us-east-1 como ponto de partida — se o Render acabar hospedado em Oregon, prefira aws-us-west-2 para reduzir a latência entre banco e API. É uma escolha de proximidade, não uma regra fixa.

Copiar a connection string no formato que o .NET lê, não no formato postgres:// que o Neon mostra por padrão. O .NET espera pares chave=valor separados por ponto e vírgula:

Host=ep-xxxx.us-east-2.aws.neon.tech;Database=planoteca;Username=neondb_owner;Password=SENHA;SSL Mode=Require;Trust Server Certificate=true

O sufixo SSL Mode=Require;Trust Server Certificate=true é obrigatório — o Neon exige conexão criptografada.

Aviso

O Neon hiberna sem tráfego. A primeira consulta depois da hibernação demora alguns segundos. Não é erro.

Não é preciso rodar migration à mão. A API aplica as migrations no próprio arranque — context.Database.MigrateAsync() em Program.cs — porque o Render (plano gratuito) não tem um passo de release separado do processo web.

02 Cloudflare R2 — arquivos

Criar um bucket chamado planoteca-planos. O nome está fixo no render.yaml; alterar o nome do bucket exige alterar esse arquivo também.

Criar um API Token do tipo Object Read & Write, com escopo restrito a esse bucket. Anotar três valores: Account ID, Access Key ID e Secret Access Key.

Habilitar o domínio público do bucket (subdomínio r2.dev ou domínio próprio). Essa URL vira UrlPublicaBase — guarde-a sem barra final.

Por quê público

A leitura do PDF é anônima por decisão de produto: baixar plano nunca exige conta. É a mesma regra do acervo, agora na camada de armazenamento.

Configurar o CORS do bucket para liberar o domínio do Vercel no método PUT. O upload do PDF vai do navegador direto para o R2, por URL pré-assinada — a API só assina a URL, não recebe o arquivo. Sem esse CORS, a catalogação falha no navegador, com o erro visível só no console.

03 Firebase — login

Criar um projeto novo. Anotar o Project ID — não o nome de exibição do projeto, que pode divergir.

Em Authentication → Sign-in method, habilitar dois provedores: Google e e-mail/senha. Os dois, não um.

Registrar um app do tipo Web dentro do projeto, para obter apiKey e authDomain.

Em Authorized domains, acrescentar o domínio que o Vercel vai gerar. Sem esse passo, o login falha com auth/unauthorized-domain — e só depois da seção 05 esse domínio existe.

Nota

Os três valores do front — apiKey, authDomain, projectId — são públicos por natureza: viajam no bundle do navegador, e o Firebase conta com isso. O que protege o projeto é a lista de domínios autorizados, nunca o segredo desses campos.

Autenticação não é autorização

O Firebase prova quem é a pessoa. O papel — professor ou administrador — mora na coluna pessoa.papel do nosso banco. Nunca use custom claim do Firebase para papel: o console dele é um lugar onde alguém altera permissão sem passar por revisão.

04 Render — API

Conectar o repositório. O Render lê o render.yaml da raiz sozinho, sem configuração adicional.

No painel, preencher as variáveis marcadas sync: false no arquivo. São sete:

VariávelDe onde vem
ConnectionStrings__DefaultConnectionNeon, seção 01
Armazenamento__R2__AccountIdR2, seção 02
Armazenamento__R2__AccessKeyR2, seção 02
Armazenamento__R2__SecretKeyR2, seção 02
Armazenamento__R2__UrlPublicaBaseR2, domínio público, sem barra final
Firebase__ProjectIdFirebase, seção 03
Cors__OrigensPermitidas__0Vercel — só existe depois da seção 05

O duplo sublinhado é como o .NET lê seção aninhada a partir de variável de ambiente: Armazenamento__R2__AccountId vira Armazenamento:R2:AccountId na configuração da aplicação.

O sufixo __0 é o índice do array de origens permitidas. Um segundo domínio entraria como __1.

Cuidado — CORS ainda não dá para preencher

Cors__OrigensPermitidas__0 é a única variável que não dá para preencher agora, porque o domínio do Vercel ainda não existe. Volte aqui depois da seção 05 (seção 06). Sem ela, a tela do front carrega e fica vazia — o navegador recusa toda resposta da API, e o erro só aparece no console. Lista vazia significa nenhuma origem permitida, e isso é de propósito: um front que não carrega denuncia a variável esquecida, enquanto um curinga a esconderia.

Anotar a URL que o Render devolve ao final do deploy, algo como https://planoteca-api.onrender.com.

Aviso

O plano gratuito hiberna após 15 minutos sem tráfego. A primeira requisição depois disso leva cerca de 50 segundos. Não é erro.

05 Vercel — front

Importar o repositório com Root Directory: planoteca-web. Sem esse ajuste, o build não encontra o package.json.

Framework: Vite, detectado sozinho. O vercel.json já trata o fallback de SPA.

Cuidado — variável de build

VITE_URL_API é obrigatória em tempo de build. Definir depois do primeiro deploy não adianta — é preciso refazer o build inteiro. Defina antes de disparar o primeiro deploy.

VariávelValor
VITE_URL_APIURL do Render, sem sufixo e sem barra final — o próprio cliente HTTP do front acrescenta /api/v1 a cada chamada
VITE_FIREBASE_API_KEYFirebase, app Web
VITE_FIREBASE_AUTH_DOMAINFirebase, app Web
VITE_FIREBASE_PROJECT_IDFirebase, Project ID

Exemplo de valor correto: https://planoteca-api.onrender.com — não .../api/v1. O prefixo já está fixo dentro de src/shared/api/cliente.ts, e duplicá-lo na variável faria toda chamada bater em /api/v1/api/v1/....

As três variáveis do Firebase são "as três juntas, ou nenhuma": configuração pela metade faz a leitura de ambiente do front devolver firebase: null, e o login some da tela sem nenhum erro claro.

06 Voltar ao Render

Preencher Cors__OrigensPermitidas__0 com a URL que o Vercel gerou, sem barra final. Disparar um redeploy da API para a variável entrar em vigor.

07 Primeiro administrador

Todo cadastro nasce professor. Não existe caminho de código que crie um administrador — é de propósito: o primeiro administrador nasce por SQL, fora da aplicação.

  1. Entrar uma vez pelo front, com Google ou e-mail/senha. Isso cria a linha correspondente em pessoa.
  2. Rodar no console SQL do Neon: 
    update pessoa set papel = 'administrador' where email = 'SEU-EMAIL-AQUI';
  3. Sair e entrar de novo. O papel entra no principal da sessão quando a API resolve a sessão de novo — a sessão antiga não sabe do UPDATE.
RotaAcesso
/admin/moderacaoadministrador
/admin/planosadministrador
/admin/catalogaradministrador
/admin/escreverqualquer conta autenticada

08 Conferir que subiu

Troque {API} pela URL do Render nos itens abaixo.

  • GET {API}/api/v1/vocabulary responde 200 sem token
  • GET {API}/api/v1/lesson-plans responde 200 ou 204 sem token
  • GET {API}/api/v1/auth/me responde 401 sem token
  • A Biblioteca abre no Vercel sem exigir login
  • Um link direto como /biblioteca?componente=matematica abre sem 404 — isso prova que o fallback de SPA está funcionando
  • O botão Entrar abre a tela de login com a opção Google visível
  • Depois do UPDATE em SQL e de entrar de novo, o menu mostra Moderação e Planos

09 O que fica de fora

CI/CD fica para depois de a API estar de pé. Domínio próprio também não entra neste primeiro deploy.

Dívida conhecida

Se a catalogação falhar depois do upload, o arquivo fica órfão no R2 — subiu, mas nenhum registro no banco aponta para ele. Ainda não existe uma rotina de coleta para esse caso.
