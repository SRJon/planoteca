Boilerplate de front-end fotus-default-web

origemcsc-importacao-web-react parfotus-default-api React 19 · Vite · TypeScript estrito docs/plans/2026-08-06-boilerplate-front.md

A fundação do front-end de importação ficou pronta e é boa demais para servir um projeto só. Esta spec descreve como extrair dela um boilerplate genérico, par do fotus-default-api, que nasce por um comando.

Resumo

O repositório csc-importacao-web-react vira fotus-default-web. Sai tudo que fala de importação. Fica a fundação: 15 componentes de interface com teste, cliente HTTP, tema, camadas com fronteira imposta por lint, e a bateria de verificação.

Entra uma fatia de exemplo chamada pessoa, que consome o /api/v1/person-samples — o próprio exemplo do back-end boilerplate. Os dois passam a formar um par que funciona ponta a ponta no primeiro dia.

Um projeto novo nasce de New-Project.ps1, o mesmo ritual que o time já usa no back-end.

01 Problema

A fundação do csc-importacao-web-react custou caro e resolve problemas que todo projeto de front-end enfrenta. Autenticação, guarda de rota, tema, tabela densa, paginação, formulário, erro de API, fronteira entre camadas e uma bateria de verificação que roda sem rede.

Hoje esse valor está preso a um domínio. Quem começa o próximo front-end da Fotus copia o repositório à mão e remove o que é de importação. Semanas depois descobre o que faltou remover. O back-end já resolveu isso com o fotus-default-api e o New-Project.ps1. O front-end não tem par.

O que agrava

O csc-importacao-web-react continua vivo e em produção. Ele evolui por conta própria. Cada semana sem o boilerplate aumenta a distância entre a fundação e a cópia que alguém fará dela.

02 Escopo

Dentro

  • Criar DEV/boilerplate/fotus-default-web como repositório git novo, sem remote.
  • Remover o domínio de importação do código, dos testes e da documentação.
  • Reduzir o tema às duas variantes claro e escuro.
  • Trocar o contrato de autenticação para o TokenDto do back-end boilerplate.
  • Trocar a matriz de permissão do Sankhya por grupos.
  • Escrever a fatia de exemplo pessoa contra /api/v1/person-samples.
  • Escrever contracts/openapi-v1.json à mão e gerar os tipos dele.
  • Escrever New-Project.ps1.
  • Reescrever README.md, CLAUDE.md e CONTRIBUTING.md.

Fora

  • Alterar o csc-importacao-web-react. Ele é somente leitura nesta tarefa.
  • Alterar o fotus-default-api. O front se adapta ao contrato dele.
  • Criar o repositório no GitHub e publicar. O git nasce local, sem remote.
  • Trocar a paleta por cor neutra. O boilerplate é da Fotus e mantém o azul e o dourado.
  • Adicionar biblioteca nova. O conjunto de dependências fica como está.

03 Solução

Os dois boilerplates viram um par. Cada um gera o seu projeto pelo próprio script, e os dois projetos gerados falam o mesmo dialeto HTTP sem ajuste nenhum.

3.1 O que passa intacto

Esta é a maior parte do repositório, e é o que dá valor ao boilerplate. Nenhum destes blocos cita importação.

Verificado

O verifica-tokens.mjs e o eslint.config.js não citam nome de domínio. O primeiro proíbe cor literal fora de tokens.css, raio fora da escala e z-index numérico. O segundo impõe a ordem das camadas e o ponto de entrada de cada fatia. Os dois passam sem alteração.

3.2 O que sai

Vinte e dois arquivos, cerca de 1.412 linhas: entities/projeto, entities/empresa, features/filtrar-projetos, pages/projetos, app/shell/empresas.ts e EscopoEmpresaProvider.tsx.

Saem junto o seletor de empresa na barra superior, os ícones solar e textil, e a pasta docs/ inteira. Sai também o contracts/openapi-v1.json atual, com 12.454 linhas geradas da API real. Sai junto o src/shared/api/schema.d.ts que nasceu dele: sem o contrato de origem, o arquivo gerado fica órfão. A Task 6 escreve os dois de novo, na ordem certa.

3.3 A fatia de exemplo

O fotus-default-api já traz o próprio exemplo: PersonSampleController, em /api/v1/person-samples. Ele aceita page, per_page, sort e filter do FilterDto, e devolve o total no cabeçalho X-Total-Count.

O front atual já manda exatamente esses quatro parâmetros. A fatia pessoa nasce dessa correspondência, e não de dado fabricado.

CamadaArquivoPapel
entitiespessoa/modelo.tsO tipo do domínio. Sete campos, e o id é Guid, não inteiro
entitiespessoa/mapeador.tsConverte o DTO gerado para o domínio. É o único arquivo da fatia que importa schema.d.ts
entitiespessoa/api.tsRecebe o Cliente por parâmetro e devolve domínio
entitiespessoa/usePessoas.tsA consulta do TanStack Query
featuresfiltrar-pessoas/Estado do filtro na URL e tradução da ordenação
pagespessoas/Monta tabela, paginação e filtro num fluxo

Duas armadilhas do controller

O GET devolve 204 sem corpo quando o total é zero, e não 200 com lista vazia. O cliente.listar já absorve esse caso.

O sort pede o nome da propriedade em PascalCase, com prefixo - para descendente. Exemplo: -FirstName. O ordenacaoApi.ts já faz essa tradução; basta alterar o mapa de campos.

3.4 Autenticação e permissão

O back-end boilerplate não expõe login. Ele verifica o bearer contra um UserinfoEndpoint externo e guarda o resultado em cache. Os DTOs de autorização, porém, já estão declarados. O front assume esse contrato:

RotaRespostaUso no front
POST /api/v1/auth/loginTokenDtoCinco campos: access_token, token_type, expires_in, refresh_token e id_token. O access_token vai no cabeçalho; o expires_in define a expiração da sessão
GET /api/v1/auth/userinfoUserInfoDtogroupMembership alimenta o menu e a guarda de rota

A expiração passa a vir de expires_in, e não de decodificar a claim exp do JWT. Isso encurta o deposito.ts: some a decodificação de claims, e some o risco de tratar um token malformado como válido.

Regra que o boilerplate carrega

Permissão aqui desenha interface. Ela esconde o que não cabe e evita caminho sem saída. Ela não autoriza nada. A autorização real é do servidor, por operação, e cobre também o GET. Quem alcançar a URL direta tem de esbarrar no servidor, nunca no menu.

3.5 O script de geração

O New-Project.ps1 repete o ritual do back-end. O código carrega dois marcadores literais, como o Fotus.Default de lá:

MarcadorOnde apareceVira
fotus-default-webpackage.json, package-lock.json, .env.example, READMEO valor de -Name
Fotus Defaultindex.html, Marca.tsx, cabeçalho do READMEO valor de -Titulo
 
.\New-Project.ps1 -Name acme-financeiro-web `
                  -Titulo "Acme Financeiro" `
                  -OutputPath C:\DEV\acme-financeiro-web

O script copia, substitui os dois marcadores, remove .git, node_modules, dist, coverage, .env.local e a si mesmo. Depois imprime os próximos passos.

Por que a fatia de exemplo fica no projeto gerado

Remover a fatia por script é frágil: ela toca rota, menu e simulação de rede, e uma remoção parcial quebra em silêncio. O README traz a lista dos caminhos a remover quando a primeira tela real nascer. Uma lista que o humano segue é mais honesta que uma opção que falha sozinha.

07 Critérios de aceite

No boilerplate

  • npm ci termina sem erro
  • npm run lint passa, incluindo o verificador de tokens
  • npm run typecheck passa nos três tsconfig
  • npm test passa, e a fatia pessoa tem teste próprio
  • npm run api:check confirma que schema.d.ts bate com o contrato
  • npm run build gera o artefato
  • npm run e2e passa nos três specs
  • npm run dev sobe, o login funciona pela simulação e a tela de pessoas lista, pagina e filtra
  • Nenhuma ocorrência de importacao, projeto, CODEMP, sankhya ou Litoral fora de um comentário histórico justificado

No projeto gerado

  • O script cria o destino e recusa destino que já existe
  • O destino não tem .git, node_modules nem New-Project.ps1
  • package.json e index.html carregam o nome e o título passados
  • Nenhuma ocorrência de fotus-default-web nem de Fotus Default sobra no destino
  • A bateria inteira do critério anterior passa dentro do destino

08 Lacunas declaradas

Duas coisas ficam abertas de propósito. O boilerplate as declara em vez de fingir que as resolve.

LacunaQuem fecha
O fotus-default-api não tem POST /api/v1/auth/login nem GET /api/v1/auth/userinfo O back-end, num trabalho separado. O contrato exato fica escrito no CLAUDE.md do boilerplate
O PersonSampleController tem [Authorize] comentado O back-end. Enquanto isso o front manda o cabeçalho e a API ignora, o que não quebra nada
